## Fulfillment inbound identity isolation — October 28 night audit

**New source-reproduced failure (before this proposed change):** F-06, F-09, and F-11 each called `resolveClient(db, event)` directly for an already-downstream `mail.response` or `docs.received` event. That function calls `patchClientContact` on an explicit `clientId` *before* verifying its organization, can insert an unknown email as a new client and best-effort sync it to the CRM. These workflows must never convert a bank reply or document receipt into a new lead or patch another organization's existing customer. F-06 can additionally queue SMS/email; F-11 can assign tasks and move funding cards; F-09 can set a no-path hold. This is a source-level security and fulfillment-isolation issue, **not proof that exploitation happened in production**. The correct safe resolver already exists as `findClient` in `src/handlers/purchase-routing.mjs`, used by F-01 and other paid downstream flows.
